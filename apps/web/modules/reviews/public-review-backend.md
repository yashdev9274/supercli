# Anonymous public reviews

`GET /api/public-reviews?url=...` previews the public PR and complete text patches without AI. A completed, unexpired review for the same head and input is included if cached. `POST /api/public-reviews` accepts only `{ "url": "..." }`, runs the shared review-generation pipeline, and returns the same payload with Markdown. Dates are ISO strings. Failures return `{ "error": "..." }` with a safe status and, when applicable, `Retry-After`.

## Deployment

Apply `packages/db/prisma/migrations/20261005120000_public_reviews/migration.sql` and regenerate Prisma before deploying. The dedicated `public_review_cache` and `public_review_quota` tables have no relations to accounts, users, connected repositories, billing, or authenticated review records. Missing tables or unavailable storage fail closed before any GitHub fetch or generation. Model/provider credentials and model selection use the existing gateway configuration. GitHub requests never send authorization; no GitHub service token is required or supported.

On Vercel, client buckets use a SHA-256 digest of the platform-overwritten `x-forwarded-for` address. On other hosts, all callers share one client bucket rather than trusting spoofable headers. The global counters always apply. A non-Vercel deployment needs a reviewed trusted-ingress integration before enabling per-IP buckets.

## Default bounds

- GitHub fetch requests: 10 globally per UTC hour, 10 per client per UTC hour. Every GET or POST, including cache hits and pending duplicates, reserves a fetch request before network access. These loading requests are separate from the daily new-review allowance; quota errors identify the exhausted lane.
- AI reservations: 10 globally per UTC hour, 20 globally per UTC day, 10 per client per UTC day. Failed/stale attempts keep their usage charge; this is internal anonymous-service usage, never a user credit or bill. Cached reviews do not consume an AI reservation. The client daily allowance is checked before shared AI budgets so its denial identifies the daily limit accurately.
- Two simultaneous generations, five-minute leases, one-minute failure cooldown, 24-hour completed-cache TTL, and 256 live cache entries. Expired entries/counters are cleaned opportunistically in transactions.
- Fifty files, 2,500 added/deleted lines, 120,000 diff characters, 8,000 PR-description characters, 150,000 prompt characters, 100,000 output characters. GitHub responses are streamed with a 1 MB per-response and 2 MB aggregate ceiling. Missing, binary, or truncated text patches are rejected instead of partially reviewed. Metadata-only renamed/copied/unchanged files require an unchanged base blob SHA, verified using one bounded Git tree request with at most 10,000 entries and no truncation.
- POST generation has a 240-second abort deadline and the route declares `maxDuration = 300`. Each model call uses the existing 8,192-token output limit and at most four model/provider attempts. A sequence-diagram repair can make one additional call through the same bounded generator.

The optional environment variables below override usage limits. They accept nonnegative integers; zero blocks new requests or generation reservations in that lane, rather than making it unlimited. Invalid values fail closed. Other size, cache, and timing bounds remain fixed.

| Variable | Default | Maximum |
| --- | ---: | ---: |
| `PUBLIC_REVIEW_FETCH_GLOBAL_HOURLY` | 10 | 60 |
| `PUBLIC_REVIEW_FETCH_CLIENT_HOURLY` | 10 | 60 |
| `PUBLIC_REVIEW_AI_GLOBAL_HOURLY` | 10 | 100 |
| `PUBLIC_REVIEW_AI_GLOBAL_DAILY` | 20 | 1000 |
| `PUBLIC_REVIEW_AI_CLIENT_DAILY` | 10 | 100 |
| `PUBLIC_REVIEW_MAX_CONCURRENT` | 2 | 10 |

The unauthenticated GitHub API usually allows only 60 requests/hour per egress IP. A preview costs four upstream requests; a new review costs five. The browser uses one preview and one generation request for a fresh review, so the default shared loading limit permits up to five fresh browser reviews per hour, or ten across two hourly windows. A metadata-only change adds one tree request. Keep the default global fetch ceiling unless the hosting egress budget is understood; increasing it can exhaust GitHub's public allowance even when daily AI allowance remains available.

Cache keys contain the canonical repository/PR and head SHA under a fixed `public-review:` namespace. Input hashes also cover base SHA, description, title, file summary, and full patches, so a changed merge base or PR text invalidates an otherwise unchanged-head cache entry. Database advisory transaction locks serialize quota/cache reservations; contending reservations return 429 with a short retry instead of occupying connections waiting for the lock. Atomic conditional quota upserts run in the same transaction as cache claims, database time defines quota windows, and lease-token checks prevent late workers from publishing over newer attempts. No repository code is executed, external links are fetched, GitHub writes are made, private context is retrieved, or connected tokens are resolved. The generator treats repository/PR text as untrusted data.

POST requires a matching Origin, rejects cross-site browser requests, and caps JSON bodies at 4 KB with a ten-second body deadline. Development-only HTTP localhost curl requests can omit Origin. Successful responses are `no-store` and do not set CORS permissions.

## Authenticated manual publishing

`POST /api/public-reviews/publish` accepts only `{ "url": "https://github.com/owner/repo/pull/123", "headSha": "<40 hex characters>", "reviewHash": "<64 hex characters>" }`. The browser hashes the exact displayed Markdown after trimming it, using SHA-256 over UTF-8. The server never accepts client Markdown or generates a new review while publishing. It responds with `{ "commentUrl": "..." }`, or adds `"alreadyPosted": true` when the same complete comment already exists.

The route requires `auth.api.getSession({ headers: request.headers })` before any source network or cache/quota access. Its only credential resolver is `getGithubTokenForUser(session.user.id)`. It doesn't look up a connected repository, another user's credentials, or an installation/service token. Missing sessions, missing GitHub connections, and GitHub's 401 return HTTP 401 with `{ "error": "...", "code": "GITHUB_CONNECT_REQUIRED", "redirectUrl": "/dashboard" }`. Permission failures are 403, missing/stale generated cache or head/hash mismatches are 409, and quota/abuse denials are 429. All errors are sanitized JSON, responses are `no-store`, and applicable errors carry `Retry-After`. This endpoint uses the same strict Origin/local-development curl policy, a 4 KB JSON ceiling, and a ten-second body deadline.

After authentication and token resolution, a separate durable publishing reservation precedes source fetching. Publishing reuses the existing public-only GitHub snapshot validator with a client authenticated solely as the session user. The repository metadata must be public before any PR/code fetch, and the PR base repository is checked again before loading patches. `publicReviewCacheIdentity` covers the current head, base, title, description, file summary, and diff. Only a matching unexpired completed cache entry can be posted, and its trimmed Markdown hash must match the displayed hash. Before the write, the complete public snapshot is fetched and compared again, and the durable lease and request deadline are checked. A later GitHub push can still race the actual issue-comment request; the comment explicitly links the reviewed commit rather than claiming to approve the current PR.

The authenticated publisher uses only the session user's token for the two public snapshot validations, `GET /user`, bounded issue-comment listing, and one explicit issue-comment `POST` or `PATCH`. A revoked token returns the same connection-required 401 contract even during metadata fetching. It does **not** invoke the existing automated sticky-comment helper, submit a pull-request review, approve/request changes, create inline threads, call `reserveGeneration`, or charge billing/AI credits. Private repositories are rejected before PR/code fetching even when the user can access them. The anonymous GET/POST implementation remains unchanged and sends no authorization.

Manual comments begin with a distinct `supercode-public-review:v1` marker containing the authenticated GitHub user ID, reviewed head, and review hash. Only comments whose author ID matches `GET /user`, whose author type is `User`, and whose manual marker embeds that same user ID are eligible for reuse/update. `performed_via_github_app` records provenance, not ownership: a GitHub App user access token can create a human-owned comment with that field populated, and those manual comments are confirmed and reused normally. Bot authors, foreign users, and all automatic review markers remain excluded. Identical complete comment bodies return their existing URL without consuming a write allowance; changed generated reviews update that user's manual comment. Searches follow at most five locally constructed pages of 100 comments, never follow arbitrary Link URLs, and refuse to write if the search is incomplete. Response bodies are streamed with a 1 MB per-response and 6 MB aggregate authenticated-response limit. The complete generated Markdown, Supercode branding, and reviewed commit link must fit 65,536 UTF-8 bytes; oversize reviews are rejected, not truncated.

Publishing uses existing `PublicReviewQuota` rows and short-lived `PublicReviewCache` lease rows under the separate `public-review-publish:` namespace, with no additional schema/migration. Quota subjects are hashed user IDs, not spoofable client/IP headers. Fixed limits are 30 source-fetch attempts per user/hour and 120 globally/hour; 10 write attempts per user/hour, 50 per user/day, and 100 globally/hour. Failed source/write attempts remain counted; anonymous loading and AI budgets are neither consulted nor consumed. Publishing's source loads use the user's authenticated GitHub allowance rather than the shared unauthenticated egress allowance, so they don't exhaust free browsing/review capacity. The two public snapshots retain the existing aggregate 2 MB response ceiling within the publisher's overall 6 MB response bound.

Nonblocking database advisory transactions atomically enforce two concurrent publish attempts per user and eight globally. Locks are scoped to user plus canonical PR, expire after 120 seconds, and use random ownership tokens so a late worker cannot release a newer attempt's lock. Requests have a 90-second overall abort deadline (`maxDuration = 120`); each GitHub request has a 15-second deadline. Database outages, missing tables, expired locks, quota failures, incomplete comment searches, and invalid GitHub data fail closed. Writes have no implicit retries. A timeout or ambiguous GitHub write response tells the user to check the PR before retrying; the next attempt searches the owner-scoped marker to avoid a second comment.

`public-review-publish.test.ts` exercises the injected handler/fetch/cache/lease boundary without live GitHub or AI calls. `public-review-publish-store.test.ts` exercises the actual store logic against injected transactional storage, including durable counter/lease restart behavior, expiry, quota rollback, and fail-closed storage. These tests do not mutate a real database or apply migrations.
