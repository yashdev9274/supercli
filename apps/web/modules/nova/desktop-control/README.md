# Desktop control broker

No OS execution is provided. All HTTP routes return 503 until the broker, device consent and end-to-end execution are integrated and verified. The proposed endpoints below require TLS at the deployment edge. Browser operations require a same-origin request and an authenticated user; device operations use signed proofs. No user ID is accepted from a request body as authority. The backend does not import or execute any Cua adapter.

All endpoints are POST, accept bounded strict JSON and return `Cache-Control: no-store`. Browser endpoints under `/api/nova/desktop-control` are `/enrollments` (`{ organizationId }`), `/devices/list` (`{ organizationId }`), `/devices/revoke` (`{ organizationId, deviceId }`), and `/commands` (`{ organizationId, deviceId, sessionId, runId, invocationId, expiresAt }`, with an ISO timestamp). `/enroll` accepts the enrollment proof below. `/device/poll`, `/device/claim`, `/device/start`, and `/device/complete` accept device proofs. User-selected organizations are always checked against an active membership. Endpoint errors are generic.

`issueEnrollment(userId, organizationId)` returns a 32-byte random base64url code and its five-minute expiry. `enrollDevice({ code, publicKey, signature, displayName })` verifies Ed25519 possession and atomically consumes the code. `publicKey` is unpadded base64url DER SPKI; `signature` is unpadded base64url Ed25519. Sign UTF-8 JSON for the array `["nova-desktop-enrollment-v1", sha256base64url(code), publicKey]`, with `code` hashed as its UTF-8 encoded string.

`enqueueCommand({ userId, organizationId, deviceId, sessionId, runId, invocationId, expiresAt })` is a trusted server call after explicit user opt-in. Expiry must be in the next two minutes. It requires an active or sleeping session with this active run, an `executing` desktop-targeted run and an `executing` invocation. `awaiting_input` is never execution authority. The broker independently hashes arguments with `normalizedArgsHash` and also checks the invocation's own hash: harness invocations use `stableHash({ name, args })`, other invocations use `normalizedArgsHash(args)`. No route currently grants or invokes this opt-in. Current web turns create runs with target `none`, so a future authorized integration must explicitly bind the selected device and target before enqueueing.

`deviceOperation(proof)` takes `{ deviceId, operation, commandId, fence, result, timestamp, nonce, signature }`. Operations are `claim`, `start`, and `complete`. The nonce is 32 random bytes in unpadded base64url; timestamp is integer Unix milliseconds within 60 seconds of server time. The signature is over UTF-8 `JSON.stringify(["nova-desktop-request-v1", deviceId, operation, commandId, fence, result, timestamp, nonce])`. The signed JSON result must be serializable; the whole message is limited to 64 KiB. `claim` requires null fence/result and returns the arguments, binding, expiry and an opaque fence. `start` requires that fence and null result; `complete` requires the fence and a non-null JSON result. An executor must start only after a successful `start` response, execute at most once, and never retry execution after an uncertain response. A claim or start that is lost remains consumed and is never reassigned. No recovery/reconciliation protocol is implemented.

`/device/poll` takes `{ deviceId, timestamp, nonce, signature }`; sign UTF-8 `JSON.stringify(["nova-desktop-poll-v1", deviceId, timestamp, nonce])`. It returns only eligible queued command IDs and expiry for that enrolled device, not arguments. The same per-device nonce namespace is used for polling and command operations. A command is never requeued after claim. Only `nova-harness:list_apps` and `nova-harness:list_windows` with empty objects, and `nova-harness:get_window_state` with exactly integer `pid` and `window_id` in the documented numeric ranges, are eligible; no other actions dispatch. These are broker data contracts and do not invoke an adapter.

Every operation rechecks active membership, device revocation, session, executing run and invocation, argument hashes and expiry within a serializable database transaction. The state update checks expiry against PostgreSQL's wall clock, including after a lock wait. A response may arrive after expiry, so a device must also check the deadline immediately before execution. The nonce is recorded transactionally and retained indefinitely. Serialization conflicts and unique constraint failures must be treated as denial, never silently retried as execution. Once a start response is delivered, later revocation or expiry cannot physically stop an already running device; an executor must independently stop on expiry and revoke notifications are not implemented. Results remain on the bound command and no result retrieval API exists; any future retrieval must independently authorize the command's owner and active membership. Mock tests do not establish PostgreSQL concurrency behavior; integration tests and deployment-level rate limits are required before production exposure.
